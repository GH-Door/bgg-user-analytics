# 재수집 표본 설계 근거

**작성일**: 2026-08-18 · 대상: 트랙 B(토큰 발급 후 실제 재수집) 유저 표본

## 왜 194,643명 전체를 안 긁는가

후보 풀(`user_list.csv`)은 194,643명이지만, 유저당 `user`+`collection` API 각 1회(합 ~10초/명, `MIN_INTERVAL_SEC=5초` 기준)를 순차 호출하면 전체 수집에만 약 20일 이상 걸린다. BGG 공식 문서도 "요청을 최소화하라"고 명시하고 있어 전수조사는 애초에 설계 의도가 아니다. 표본을 뽑되, "시간이 없어서"가 아니라 **통계적으로 필요한 최소 크기**를 근거로 정한다.

## 표본 크기 산정 — 모비율 추정 공식

이 프로젝트의 핵심 산출물(퍼널 전환율, 세그먼트 비중, 카테고리/메커닉 선호 비율)은 전부 **비율(proportion) 추정**이다. 비율 추정에 필요한 표본 크기는 유한모집단 보정을 포함한 표준 공식으로 계산한다.

```
n0 = Z² · p(1-p) / e²
n  = n0 / (1 + (n0-1)/N)
```

| 파라미터 | 값 | 근거 |
|---|---|---|
| N (모집단) | 194,643 | `user_list.csv` 후보 풀 크기 |
| Z (신뢰수준) | 1.96 | 95% 신뢰수준 — 사용자 리서치/설문에서 통용되는 표준값 |
| p (모비율 추정치) | 0.5 | 사전 정보 없음 → 분산이 최대인 보수적 가정(가장 큰 n을 요구) |
| e (허용 오차) | ±2%p | 퍼널 전환율·세그먼트 비중 비교에 실무적으로 충분한 정밀도 |

→ **n0 = 2,401 → 유한모집단 보정 후 n ≈ 2,372.** 반올림해 **목표 유효 표본 2,400명**으로 정한다.

## 왜 층화추출이 아니라 단순무작위추출(SRS)인가

처음엔 가입연도(`yearregistered`)로 층화추출하는 안을 검토했다. 하지만 2024 폴백 데이터(`bgg_staging.stg_user_info`, 10,754명)의 가입연도 분포를 실제로 조회해보니:

| 가입연도 | 유저 수 | 비중 |
|---|---|---|
| 2000~2006 | 1~101명 | 0.01~0.9% |
| 2019~2021 | 1,220~1,643명 | 11~15% |

초기 코호트(2000~2007)는 전체의 1% 미만이다. 이 비중대로 2,400명 표본에 비례배분하면 2001년 코호트에는 2명만 할당된다. 여기에 인위적으로 "코호트당 최소 30명" 같은 하한(floor)을 두려고 했으나, **후보 풀 194,643명 안에서도 2001년 가입자 자체가 절대적으로 희소한 것으로 추정**되어(약 0.07% 추정 시 전체 후보 풀에 130명 안팎) 하한을 강제로 채우려면 스크리닝 표본을 수만 단위로 키워야 한다 — 표본 설계로 해결할 문제가 아니라 **모집단 자체의 특성**이다.

따라서 별도 층화 없이 **SRS**를 쓴다. SRS는 기댓값상 모집단의 가입연도 구성비를 그대로 보존하므로 실질적으로 "비례배분 층화"와 같은 결과를 더 간단한 절차로 얻는다. 초기 코호트가 표본에서도 희소하게 나타나는 것은 표본 설계의 한계가 아니라 **BGG 플랫폼 초기 채택자 규모가 실제로 작다는 사실의 반영**이며, 코호트 분석 리포트에 그대로 명시한다(작은 코호트의 리텐션 추정치는 신뢰구간이 넓다는 점도 함께 표기).

## 스크리닝 표본 크기 — 3,000명

목표 유효 표본은 2,400명이지만, 실제 추출된 계정 중 일부는 다음 사유로 제외될 수 있다:
- 탈퇴/비공개 계정 (API가 빈 응답 반환)
- `own=1` 기준 소유 게임 0개 (컬렉션 API 단계에서 자연 배제)
- 요청 실패(재시도 소진)

일반적인 설문 비응답 버퍼(~20%)를 적용해 **3,000명을 1차 무작위 추출**한다 (`n = 2,400 / 0.8 = 3,000`). `random.seed(20260818)`로 고정해 재현 가능하게 뽑는다.

## 진행 순서 (트랙 B)

1. **스크리닝 패스**: 3,000명에 대해 가벼운 `user` API만 호출 → 유효 계정 수·실제 가입연도 분포 확인 (`scripts/collect_phase1_screening.py`)
2. **본수집 패스**: 스크리닝에서 유효했던 계정에 대해 `collection`(own=1) API 호출 → `item_info`/`user_item` 갱신
3. **thing 배치 수집**: 위에서 나온 `objectid` 전체에 대해 `thing` API(20개씩 배치) 호출 → `item_details`/`item_stats`/`item_link`/`item_rank`
4. **plays 표본**: 본수집 대상 중 하위표본(가입연도 비중 유지되는 SRS 특성상 별도 재추출 불필요, 전체 또는 무작위 축소)에 대해서만 `plays` API 호출 — 페이지네이션 비용이 커서 별도 관리

각 단계는 기존 체크포인트 메커니즘(`checkpoint.py`, `_load_existing_objectids`)으로 중단 후 재개 가능하다.
